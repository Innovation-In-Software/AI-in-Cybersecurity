## Lab 1.4: AWS Security Posture Baseline

This lab establishes a practical baseline of your AWS security posture before deeper endpoint telemetry and AI workflow labs. You will enumerate real misconfigurations directly via AWS CLI, prioritize findings by risk, and perform one safe remediation.

This mirrors what a security engineer does when auditing an account quickly: query cloud APIs directly rather than waiting for Security Hub findings pipelines to populate. AWS Security Hub is the production-grade way to do this continuously, but it requires AWS Config to be running first and takes 30–60 minutes before findings appear in a fresh account — far too slow for a lab. The CLI checks in this lab produce the same findings immediately.

> **Note for production accounts:** Once AWS Config is enabled and both CIS and FSBP standards are active in Security Hub, findings like open SSH ports and IAM users without MFA appear automatically and continuously. The teardown steps at the end of this lab include instructions for enabling Security Hub if you want to explore it after completing the CLI exercises.

## Safety Rails

## Part 2: Enumerate Misconfigurations

Run each check in order. Each one targets a specific high-value control category.

### Check 1: Security groups with SSH open to the internet

```bash
aws ec2 describe-security-groups \
  --region $AWS_REGION \
  --query "SecurityGroups[?IpPermissions[?FromPort==\`22\` && ToPort==\`22\` && IpRanges[?CidrIp=='0.0.0.0/0']]].[GroupId,GroupName,Description]" \
  --output table
```

Expected: your `soc-lab-sg` security group appears. This is the finding you will remediate in Part 3.

### Check 2: Root account MFA status

```bash
aws iam get-account-summary \
  --query 'SummaryMap.{RootMFAEnabled:AccountMFAEnabled,RootAccessKeysActive:AccountAccessKeysPresent}' \
  --output json
```

`RootMFAEnabled: 0` is HIGH risk. Root access keys active is CRITICAL.

### Check 3: IAM users without MFA

```bash
aws iam generate-credential-report 2>/dev/null || true
sleep 3
aws iam get-credential-report --query 'Content' --output text \
  | base64 -d \
  | awk -F',' 'NR>1 && $8=="false" {print $1, "mfa_not_active"}'
```

Any output here is a finding: an IAM user (or root) with MFA not enabled.

### Check 4: S3 buckets with public access block disabled

First, create a lab bucket with public access block intentionally disabled so you have a guaranteed finding to detect.

```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
LAB_BUCKET="soc-lab-public-${ACCOUNT_ID}"

aws s3api create-bucket --bucket $LAB_BUCKET --region us-east-1
aws s3api put-public-access-block \
  --bucket $LAB_BUCKET \
  --public-access-block-configuration \
    BlockPublicAcls=false,IgnorePublicAcls=false,BlockPublicPolicy=false,RestrictPublicBuckets=false
echo "Lab bucket created: $LAB_BUCKET"
```

Now enumerate all buckets for disabled public access blocks.

```bash
aws s3api list-buckets --query 'Buckets[].Name' --output json | \
  jq -r '.[]' | while read bucket; do
    result=$(aws s3api get-public-access-block --bucket "$bucket" 2>/dev/null \
      | jq -r '.PublicAccessBlockConfiguration | to_entries | map(select(.value==false)) | .[].key' 2>/dev/null)
    if [ -n "$result" ]; then
      echo "FINDING: $bucket has public access block disabled for: $result"
    fi
  done
```

Expected: `soc-lab-public-<account-id>` appears in the output.

### Check 5: Verify your actions are being logged

CloudTrail Event History records management API calls for the last 90 days with no trail required. Use it to confirm the bucket you just created is already audited.

```bash
aws cloudtrail lookup-events \
  --region $AWS_REGION \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=$LAB_BUCKET \
  --query 'Events[].{Time:EventTime,Event:EventName,User:Username}' \
  --output table
```

Expected: `CreateBucket` and `PutPublicAccessBlock` events appear with your username.

You can also view this in the console: [CloudTrail → Event history](https://us-east-1.console.aws.amazon.com/cloudtrailv2/home?region=us-east-1#/events) → filter by **Resource name** → enter the bucket name.

> **What a CloudTrail trail adds:** Event History is read-only and expires after 90 days. Creating a trail delivers logs continuously to S3 (and optionally CloudWatch Logs), enabling long-term retention, SIEM ingestion, alerting on specific API calls, and data event logging (S3 object reads/writes, Lambda invocations) which Event History does not capture.

## Part 2b: Build Findings CSV

```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
echo 'severity,title,resource_type,resource_id,status' > baseline_top_findings.csv

# Check 1: SSH open to internet
SG_LIST=$(aws ec2 describe-security-groups \
  --region $AWS_REGION \
  --query "SecurityGroups[?IpPermissions[?FromPort==\`22\` && ToPort==\`22\` && IpRanges[?CidrIp=='0.0.0.0/0']]].GroupId" \
  --output text)
for sg in $SG_LIST; do
  echo "HIGH,SSH open to 0.0.0.0/0,AWS::EC2::SecurityGroup,$sg,FAILED" >> baseline_top_findings.csv
done

# Check 2: Root MFA
ROOT_MFA=$(aws iam get-account-summary --query 'SummaryMap.AccountMFAEnabled' --output text)
if [ "$ROOT_MFA" = "0" ]; then
  echo "CRITICAL,Root account MFA not enabled,AWS::IAM::Account,arn:aws:iam::${ACCOUNT_ID}:root,FAILED" >> baseline_top_findings.csv
fi

# Check 3: IAM users without MFA
aws iam generate-credential-report 2>/dev/null || true ; sleep 3
aws iam get-credential-report --query 'Content' --output text \
  | base64 -d \
  | awk -F',' 'NR>1 && $8=="false" {
      print "HIGH,IAM user MFA not enabled,AWS::IAM::User," $1 ",FAILED"
    }' >> baseline_top_findings.csv

# Check 4b: IAM users/groups/roles with AdministratorAccess attached
aws iam list-entities-for-policy \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess \
  --query '{Users:PolicyUsers[].UserName,Groups:PolicyGroups[].GroupName,Roles:PolicyRoles[].RoleName}' \
  --output json | jq -r '
    (.Users[]? | "HIGH,AdministratorAccess attached to user,AWS::IAM::User," + . + ",FAILED"),
    (.Groups[]? | "MEDIUM,AdministratorAccess attached to group,AWS::IAM::Group," + . + ",FAILED")
  ' >> baseline_top_findings.csv

cat baseline_top_findings.csv
```

Prioritization rule for this lab:

1. CRITICAL/HIGH severity first.
2. Internet-exposed resources next.
3. Identity misconfiguration next.
4. Logging/monitoring gaps next.

## Part 3: Controlled Remediation Example (Security Group SSH Scope)

This remediation narrows SSH access from broad internet scope to your current public IP.

1. Find your current public IP.

```bash
MY_IP=$(curl -s https://checkip.amazonaws.com)
echo "$MY_IP"
```

2. Identify target security group (replace SG_ID).

```bash
export SG_ID=sg-REPLACE_ME
aws ec2 describe-security-groups --group-ids $SG_ID --region $AWS_REGION
```

3. Revoke broad SSH rule if present.

```bash
aws ec2 revoke-security-group-ingress \
  --group-id $SG_ID \
  --protocol tcp \
  --port 22 \
  --cidr 0.0.0.0/0 \
  --region $AWS_REGION || true
```

4. Add restricted SSH rule.

```bash
aws ec2 authorize-security-group-ingress \
  --group-id $SG_ID \
  --protocol tcp \
  --port 22 \
  --cidr ${MY_IP}/32 \
  --region $AWS_REGION
```

5. Verify final ingress rules.

```bash
aws ec2 describe-security-groups --group-ids $SG_ID --region $AWS_REGION \
  --query 'SecurityGroups[0].IpPermissions' --output json
```

## Part 3b: Review Security Hub Findings

By now Security Hub has been running for 20–40 minutes. Open the console and compare what it found against your CLI baseline.

1. Open [Security Hub → Findings → All findings](https://us-east-1.console.aws.amazon.com/securityhub/home?region=us-east-1#/findings).

2. Filter by **Record state = ACTIVE** and sort by **Severity** descending.

3. Look for these findings that match your CLI checks:
   - **`soc-lab-sg` SSH open to internet** → `EC2.19` (FSBP) or CIS 4.1/4.2
   - **IAM user MFA not enabled** → `IAM.5` (FSBP)
   - **Root credential usage** → GuardDuty `Policy:IAMUser-RootCredentialUsage` (GuardDuty is enabled in Lab 1.5 — if you are completing this lab in sequence, this finding will not appear here until after that lab)
   - **S3 public access block disabled** → `S3.1` (FSBP)

4. Notice the **SSH finding for `soc-lab-sg` should now show as resolved** (or will resolve within 30 minutes) because you restricted it to `${MY_IP}/32` in Part 3. This is how Security Hub tracks remediation state automatically.

> Config-backed findings (EC2, IAM, S3) may still be absent if Security Hub was just enabled — they require AWS Config to be running. GuardDuty findings appear immediately. Your CLI output from Part 2 remains the authoritative baseline for this lab regardless.

5. Note the total finding count and any items not covered by your CLI checks.
